## 1. Какие задачи ставились перед каждым агентом

Обоим агентам ставились одинаковые задания из `HOMEWORK.md` по проекту **Investing Demo**
(старый учебный Django-проект со справочником акций, Celery и Tinkoff Invest API):

| Задание | Постановка |
|---|---|
| №1. Анализ исходного кода | Определить назначение приложения, стек, структуру, архитектуру, зависимости, модель данных, механизмы обработки запросов и работы с БД. Результат — `ANALYSIS.md` |
| №2. Восстановление функциональных требований | Описать фактически реализованную функциональность в виде нумерованных требований с подтверждением в коде; отдельно зафиксировать неоднозначности и дефекты. Результат — `REQUIREMENTS.md` |
| №3. Модернизация, дефекты, рефакторинг | Обновить устаревшие зависимости, устранить проблемы совместимости и ошибки реализации, провести рефакторинг, запустить приложение и проверить работоспособность; при необходимости — добавить автотесты. Результат — `MODERNIZATION.md` + работающий код |
| №4. Новая функциональность | Реализовать одно из четырёх направлений (обоими агентами выбрано «Виртуальный инвестиционный портфель»): сформулировать требования, изменить модель данных, сгенерировать код, проверить отсутствие регрессий. Результат — `FEATURE_REQUIREMENTS.md`, `FEATURE_REPORT.md`, новый код и тесты |

Ключевое ограничение задания: каждый агент работал с **отдельной копией** исходного проекта
(результаты первого агента не использовались вторым), а исправление ошибок и новая
функциональность должны быть разграничены.

## 2. Возникшие проблемы и как они решались

### 2.1 DeepSeek (`deepseek-results`, `agent-deepseek/MODERNIZATION.md`)

**Проблема 1 — зависимости, которые невозможно установить.** Пакеты `tinkoff==0.1.1` и
`tinkoff-investments==0.2.0b50` в исходном `requirements.txt` больше не существуют в PyPI
(проверено запросами к `pypi.org/simple/...` — HTTP 404; репозиторий SDK заархивирован).
Кроме того, оба пакета конфликтовали по namespace `tinkoff`. Любая установка зависимостей
упадала бы на неразрешимой зависимости.

*Решение:* пакеты убраны из runtime-зависимостей; SDK вынесен в отдельный опциональный
`requirements-tinkoff.txt` с установкой из архивного репозитория
(`tinkoff-investments @ git+https://github.com/RussianInvestments/invest-python.git`);
все обращения к SDK переведены на **ленивый импорт** внутри функций
(`dashboard/services/market_data.py`, `dashboard/services/graph.py`,
`dashboard/management/commands/add_shares.py`). Приложение запускается, отдаёт UI/API и
проходит тесты без установленного SDK. Ограничение честно зафиксировано в разделе 7
MODERNIZATION.md: реальные вызовы Tinkoff API не проверялись, проверены только ветки деградации.

**Проблема 2 — приложение не запускалось в принципе.** Критические дефекты конфигурации:
пустой `SECRET_KEY` (`ImproperlyConfigured` при старте), пустой `TINKOFF_TOKEN`,
жёстко прописанный PostgreSQL, недоступный без Docker (падали `migrate`/`runserver`),
`ALLOWED_HOSTS = []`, относительный `STATIC_URL = "static/"` (CSS не грузился на вложенных
маршрутах). Полный список из 12 блокирующих проблем — в разделе 3 MODERNIZATION.md
с колонками «было/стало/файл».

*Решение:* все параметры выведены в переменные окружения (`.env.example`); по умолчанию
используется SQLite, PostgreSQL включается через `DB_ENGINE=postgres`; `ALLOWED_HOSTS`
и `DEBUG` настраиваются через env; исправлен `STATIC_URL`, добавлен `STATIC_ROOT`.

**Проблема 3 — дефекты реализации, ломающие сценарии.** Найдено и исправлено более 20
дефектов из восстановленного каталога DEF-01…DEF-42 (раздел 4 MODERNIZATION.md). Наиболее
существенные:

| Дефект | Суть | Исправление |
|---|---|---|
| DEF-10 | В шаблон передавался **класс** формы вместо экземпляра → страницы входа/регистрации без `<input>` | `AuthForm()` / `RegistrationForm()` в `user/views.py` |
| DEF-17 | Несуществующий `pk` в карточке акции → 500 | `get_object_or_404` в `dashboard/views.py` |
| DEF-18 | Ошибка Tinkoff API роняла карточку в 500 | `try/except` + сообщение «График временно недоступен» в шаблоне |
| DEF-23 | Из цены Tinkoff бралась только целая часть: `100.55` → `100` | `quotation_to_float()` (`units + nano/1e9`) в `market_data.py` и `graph.py` |
| DEF-20 | `add_shares` искал по всем полям → `IntegrityError` при переименовании бумаги | `get_or_create(figi=..., defaults={...})` |
| DEF-25 | `last_prices.pop()` → `IndexError` на пустом ответе API | явная проверка и `ValueError` с понятным текстом |

*Проверка решения:* каждый исправленный дефект покрыт тестами; дополнительно 4
регрессионных теста на прежнее поведение (`ExistingBehaviourTests` в
`agent-deepseek/dashboard/tests.py`). Прогон: `check` — без замечаний,
`makemigrations --check` — «No changes detected», `runserver` + HTTP-проверки
(`/`, `/api/v1/shares/`, `/user/login/`, `/admin/`, `/1` — все 200/404 как ожидается),
`manage.py test dashboard` — **33 теста, OK**.

**Проблема 4 — неоднозначности спецификации.** Например, расписание Celery: ключ назывался
`add-every-5-min`, а период был 10 секунд (AMB-03).

*Решение:* имя ключа приведено к смыслу задачи (`update-last-price`), период стал
настраиваемым (`PRICE_UPDATE_INTERVAL_SECONDS`, по умолчанию 300 секунд = 5 минут, как в
названии ключа) — решение и обоснование зафиксированы в разделе 3.1 MODERNIZATION.md.

**Проблема 5 — ограничение окружения.** `pip install` блокировался файловой песочницей
при распаковке колёс.

*Решение:* пакеты устанавливались распаковкой тех же колёс PyPI в виртуальное окружение;
состав и версии проверены импортом (Django 5.2.18, DRF 3.16.1, Celery 5.5.3 и т.д.).
Ограничение окружения зафиксировано, не выдано за решение проблемы проекта.

**Итог модернизации DeepSeek:** Django 4.1.7 → **5.2.18 LTS**, DRF → 3.16.1, Celery → 5.5.3,
psycopg2 → psycopg 3.3.6, plotly → 6.9.0; runtime-зависимости сокращены с 40 пакетов
(включая транзитивные и dev-инструменты) до 9 прямых; dev-инструменты — в
`requirements-dev.txt`; секреты — из кода в переменные окружения.

### 2.2 OpenCode (`opencode-results`, `agent-opencode/MODERNIZATION.md`)

**Проблема 1 — устаревшие зависимости.** В MODERNIZATION.md составлена таблица
предлагаемых обновлений (Django → 4.2.16, DRF → 3.15.2, Celery → 5.4.0, psycopg2 →
psycopg 3 и т.д.). Обновление выполнено более консервативно, чем у DeepSeek: Django 4.2 LTS
вместо 5.2, транзитивные зависимости и dev-инструменты (black, isort, tomli) остались в
`requirements.txt`.

**Проблема 2 — недоступный Tinkoff SDK и конфигурация, мешающая запуску.** Фактические
изменения (по разделам «Какие файлы добавлены/изменены» в `FEATURE_REPORT.md` и MODERNIZATION.md):

- в `config/settings.py` — `ALLOWED_HOSTS`, `SECRET_KEY` из env, БД переключена на SQLite
  для простоты запуска (PostgreSQL-конфигурация закомментирована), настройки Celery;
- в `manage.py` — исправлено устаревшее сообщение об ошибке;
- в `dashboard/tasks.py` — улучшена обработка `None`/ошибок при обновлении цен;
- в `dashboard/services/market_data.py` — добавлена проверка токена и обработка пустого ответа API
  (аналог DEF-25 у DeepSeek, но без исправления потери дробной части цены — DEF-23 не найден).

**Проблема 3 — SDK нельзя установить из PyPI.** Вместо исключения пакета из зависимостей
(как сделал DeepSeek) OpenCode оставил `tinkoff-investments==0.2.0b62` в
`requirements.txt` и создал **самодельные заглушки** `tinkoff/__init__.py`,
`tinkoff/invest/__init__.py`, `tinkoff/invest/utils.py`, `tinkoff/invest/schemas.py`
«для возможности импорта и прохождения проверок без реального SDK».

*Критика решения:* локальный каталог `tinkoff/` затеняет реальный пакет при его установке,
а сам `requirements.txt` остаётся недоустанавливаемым (пакета нет в PyPI). Проблема
замаскирована, а не решена; в MODERNIZATION.md это никак не отражено — там приведён только
план модернизации, без фактического списка исправлений и результатов проверок.

**Проблема 4 — падающий тест.** По результатам прогона «всего 15 тестов, 14 прошли
успешно, 1 тест с HTML-шаблоном (`test_share_list_html`) падает». Автор относит это к
несовместимости Django 5.1/Python 3.14 с механизмом копирования контекста шаблона в
тестовом клиенте и не исправляет — тест изменён на `assertIn(response.status_code, [200])`
в `dashboard/tests.py`, что маскирует отличие 500 от 200 (у DeepSeek тест остался строгим
`assertEqual`).

*Проверка решения:* `check` и `migrate` проходят, `runserver` запускался; тестовый прогон
неполный — функциональность HTML-сценариев фактически не подтверждена автотестами.

**Проблема 5 — недокументированные расхождения.** MODERNIZATION.md у OpenCode — это в
основном план («Предлагаемые обновления», «План модернизации» из 5 пунктов), а не отчёт о
выполненном: часть версий в таблице не совпадает с фактическим `requirements.txt`
(например, в таблице redis 5.0.8 — совпадает, но Django указан 4.2.16 при заявке
«Django 5.1.3 в окружении» в FEATURE_REPORT.md), реальные исправления и их причины
разбросаны по FEATURE_REPORT.md. Восстановить по документации полную картину «что и почему
изменено» нельзя — в отличие от DeepSeek, где каждая правка имеет номер дефекта, файл
и обоснование.

### 2.3 Общая для обоих агентов проблема — новая функциональность (задание №4)

Оба агента реализовали «Виртуальный инвестиционный портфель» и столкнулись с одинаковыми
содержательными вопросами, но решили их с разной глубиной:

| Вопрос | DeepSeek | OpenCode |
|---|---|---|
| Атомарность и конкурентность | `@transaction.atomic` + `select_for_update` вынесены в сервисный слой `dashboard/services/portfolio.py` | те же механизмы, но прямо во вьюхе `dashboard/api/v1/portfolio_views.py` |
| Отказ при продаже больше остатка | 400 с указанием остатка и запрошенного количества, тест проверяет неизменность состояния | 400 `not enough quantity`, проверка внутри транзакции с комментарием о конкурентных продажах |
| Точность расчётов | Decimal(18,6), преобразование через `str()` (устранение float-погрешности), отдельные тесты точности | Decimal с `_quantize()`, отдельной проверки точности нет |
| Позиции без цены | исключаются из итога с флагом `unpriced_positions` | ошибка при отсутствии цены только для сделки; в сводке не обработано явно |
| Тесты | 19 новых тестов, все проходят | 5 новых тестов, проходят |
| HTML-интерфейс | отсутствует (выбор API обоснован в FEATURE_REPORT.md, раздел 1) | отсутствует |

## 3. Вывод об эффективности работы каждого агента

**DeepSeek — высокая эффективность.** Агент справился со всеми четырьмя заданиями
с систематичностью, характерной для опытного инженера: каждая проблема получила
идентификацию (AMB-*/DEF-* нумерация), решение с обоснованием и проверку (тесты +
HTTP-прогон). Особенно ценны самостоятельно найденные нетривиальные вещи: недоступность
Tinkoff SDK в PyPI (проверено через внешние запросы), потеря дробной части цены,
передача класса формы вместо экземпляра. Результат полностью верифицируем: **33 из 33
тестов проходят**, запуск сервера подтверждён, каждое решение задокументировано.
Слабые места тоже честно задокументированы (разделы 1.1, 7 MODERNIZATION.md, раздел 6
FEATURE_REPORT.md) — вместо сокрытия ограничений агент их перечисляет.

**OpenCode — средняя эффективность.** Агент быстро дошёл до работающего ядра: приложение
запускается, портфель реализован корректно по основной логике (атомарные сделки,
блокировки, средняя цена, P&L), базовые требования и граничные случаи зафиксированы.
Однако качество работы неравномерное: MODERNIZATION.md — фактически план, а не отчёт;
падающий тест не исправлен, а объяснён окружением; недоступный пакет оставлен в
зависимостях с самодельной заглушкой вместо корректного решения; часть реальных дефектов
(DEF-10, DEF-23) не обнаружена. Документация переоценивает результат: заявленное «проверено,
работает» местами не подтверждается полным тестовым прогоном.

**Практический вывод.** DeepSeek предпочтителен для задач, где важны полнота анализа,
надёжность и доказуемость результата (аудит legacy, модернизация, функциональность с
высокими требованиями к качеству). OpenCode — для быстрого прототипирования и задач
с небольшим ясным объёмом, но его результаты требуют обязательной человеческой проверки:
агент склонен к «обходным» решениям и оптимистичной самопроверке. Детальное сравнение —
в `COMPARISON.md`.
